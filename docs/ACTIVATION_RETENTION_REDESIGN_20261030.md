# IterWave 激活与留存闭环改造方案

- 状态：产品/技术评审稿，未进入开发
- 基准分支：main
- 基准提交：6312f35bd7a53c5c76b572fbaf6a345c8818b355
- 日期：2026-10-30
- 范围：首次价值（TTV）、内容采用、人工发布回填、数据回收、轻量复盘
- 原则：先交付真实内容价值，再引导配置完整运营系统；不以模板伪装模型能力；不自动发布；不破坏现有生产状态机与本地数据

## 0. 结论与决策摘要

当前产品的主要问题不是缺少功能，而是新用户在看到内容质量之前，被要求完成账号画像、平台、选题库、模型、运行环境、阶段目标、检查清单等完整配置。与此同时，生成链路在模型不可用或调用失败时会静默回退到低质量模板，造成首次体验反噬。发布后的数据回收则过度依赖平台登录态，用户看不到持续复盘价值。

本次改造目标：

1. 将首次体验从“先配置完整工作台”改为“先获得可用样稿，再逐步配置”。
2. 所有正式生成必须由可用模型完成；模型不可用或失败时明确失败，不再输出模板稿。
3. 将人工发布回填作为数据回流的一等通道，平台自动读回作为增强通道。
4. 将复盘首页收敛为三项可执行结论：表现最好的一篇、可能原因、下一轮建议。
5. 建立可度量的激活、采用、发布和复盘指标，避免只统计生成数量。

## 1. 现状基线与关键发现

### 1.1 已确认的代码事实

- 首次引导位于 `web/src/pages/Onboarding.tsx`，当前包含账号画像、平台、选题库、模型配置、运行环境、阶段目标、检查清单七步。
- 生产入口位于 `web/src/pages/Production.tsx`，正式轮次依赖现有选题、计划、平台及模型配置。
- `src/core/content_pipeline.py` 的 `generate_copy_content` 当前在 LLM 不可用、调用异常或输出格式不合格时，会调用 `_generate_via_template`。模板中存在“🔥…这几点值得记下来”“别再瞎折腾了”等通用句式。
- 数据库已有 `contents`、`drafts`、`metrics` 三张核心表。指标字段允许 NULL，必须继续遵守 NULL 不等于 0 的规则。
- 数据库迁移 `017_drafts_note_url.sql` 已为 `drafts` 增加 `platform_note_url`；`POST /api/drafts/{draft_id}/publish_confirm` 已支持可选 `note_url`。因此“发布后粘贴链接”不是从零开发，重点是把入口前移、降低操作成本并补齐数据源标记/手工指标回填。
- 现有自动读回在 `src/adapters/readback.py` 中依赖平台登录态；无法读回时会形成 pending、failed 或 parse_error 状态。手工回填应与自动读回并存，而不是替代自动读回。
- 产品当前保留人工发布红线：Playwright 仅存草稿，不自动点击发布。此次改造不改变该红线。
- 现有认证模型以本地/账号组访问口令为主，并非完整的 SaaS 用户注册体系。因此早期激活统计应以“新账号组/首次初始化环境”为 cohort 单位，不得虚构用户级注册数据。

### 1.2 当前问题链

```
访问产品
  ↓
完成七步配置 + 平台登录
  ↓
运行完整生产链路
  ↓
模型缺失/异常时仍输出模板内容
  ↓
用户形成低质量第一印象
  ↓
人工发布
  ↓
自动读回依赖登录态，失败后数据长期待采集
  ↓
复盘缺少样本，用户无法看到改进价值
```

## 2. 产品定位与目标用户假设

### 2.1 本轮暂定 ICP

在审核意见中，ICP A/B 的定义和证据没有提供，不能直接采纳“选择 B”的结论。本方案先使用一个可验证的临时假设：

> 有持续图文内容需求、由本人或小团队负责账号运营、目前缺少稳定选题与内容迭代方法的创作者/小商家运营者；首期聚焦一个主战场平台。

暂不把多账号代运营机构、大型品牌营销部门、纯批量分发团队作为首期核心用户。

验证问题：
- 是否每周至少有 2-3 次内容生产需求？
- 是否愿意在生成后人工修改并发布？
- 是否愿意为“内容定位一致 + 发布后复盘”付费，而不只是为生成数量付费？
- 用户最主要的平台是否能在首轮体验中选定一个？

正式定 ICP 前，需要补齐审核原文中 A/B 的定义、目标用户访谈或至少 5-10 个真实目标用户样本。

### 2.2 核心价值主张

不强调“AI 一键生成大量内容”，改为：

> 帮助个人创作者和小团队持续写出符合账号定位的图文内容，并根据真实发布反馈改进下一轮选题和表达。

## 3. 新用户路径：快速体验与正式运营双轨

### 3.1 快速体验路径

目标：从首次打开产品到看到第一批可用样稿，目标 TTV ≤ 3 分钟（作为体验目标，不承诺模型网络延迟必然小于 3 分钟）。

用户只填写两个信息：
1. 账号是做什么的（一句话）。
2. 主战场平台（单选：小红书/抖音/快手/视频号）。

系统后台完成：
1. 校验模型服务可用。
2. 根据账号描述生成 3 个候选选题/内容角度。
3. 用户可选择一个角度，或默认各取一个方向生成 3 篇样稿。
4. 生成三篇平台适配文案，执行内容质量检查。
5. 展示三篇样稿，支持复制、保存到本地草稿区、标记不合适并反馈原因。

快速体验不要求：
- 扫码登录平台；
- 建立完整选题库；
- 配置阶段目标；
- 配置完整母计划；
- 先创建正式生产轮次。

快速体验生成的内容标记为“体验样稿”，与正式轮次内容区分；不得误触发平台存草稿、排期、自动采集等正式运营动作。用户后续进入正式运营时，可选择将体验样稿转为正式内容资产。

### 3.2 模型服务策略：必须先明确部署模式

“无模型 API Key 仍能 3 分钟出稿”不能靠前端绕过。当前项目是本地优先/自托管架构，默认没有可供所有安装实例调用的公共模型额度。

建议支持两种明确模式：

**A. 托管体验模式（需要产品运营方提供服务）**
- 由部署方配置受控的模型网关和服务端密钥。
- 浏览器端永远不接触供应商密钥。
- 每个账号组/安装实例配置明确的试用额度、速率限制、并发限制和每日上限。
- 超限后提示用户接入自己的模型，不静默降级。
- 试用前明确告知输入内容会发送至托管模型服务，说明数据处理范围和保留策略。
- 需要具备滥用防护、成本告警、熔断、审计与服务不可用提示。

**B. 自托管模式**
- 用户可以先填写账号定位和平台，但必须先接入自己的模型才能生成样稿。
- 页面明确说明“接入模型后才能生成”，提供最短模型配置入口。
- 不承诺无密钥三分钟出稿。

不得把平台内置模型额度当成通用能力；只有在部署方确实配置了托管网关时才显示托管试用入口。托管模式是否上线是产品商业决策，不是本次代码改造可自行假定的前提。

### 3.3 正式运营引导

用户完成首次样稿采用后，再逐步引导：
- 完善账号画像；
- 导入/维护选题库；
- 绑定一个主战场平台账号；
- 设置阶段目标；
- 运行正式生产轮次；
- 逐步启用其他平台和高级能力。

首次体验完成后不强制连续弹出配置向导。首页展示“距离正式运营还差哪一步”，用户可按需完成。

### 3.4 页面调整

| 页面/区域 | 调整 |
|---|---|
| 首次入口 | 增加“快速体验”主入口；完整配置移至“正式运营设置” |
| 快速体验页 | 仅账号一句话 + 主战场平台；显示模型服务状态和隐私说明 |
| 样稿结果页 | 三篇样稿卡片；复制、保存、反馈；标记体验样稿 |
| Onboarding | 保留七步能力，但改为正式运营配置，不再阻断快速体验 |
| Production | 继续作为正式轮次工作台；明确提示缺失配置，不与快速体验混用 |
| 首页/Dashboard | 展示快速体验进度、待完成正式运营配置、近期采用与发布情况 |
| 设置页 | 明确显示模型来源：托管试用/自带模型；展示额度与健康状态 |

## 4. 模型调用与内容质量门

### 4.1 生成失败策略

正式生成和快速体验统一执行以下规则：

- 未配置模型：返回明确的 `model_not_configured`，不创建伪内容。
- Key 无效/鉴权失败：返回 `model_auth_failed`。
- 额度/限流：返回 `model_quota_exceeded` 或 `model_rate_limited`。
- 超时/服务异常：返回 `model_unavailable` 或 `model_timeout`。
- 输出格式不合格：允许有限次数重试；仍不合格则失败并说明原因。
- 内容质量门不通过：进入待修改/重试状态，不进入可采用草稿。
- 不允许任何上述情况静默调用模板稿。

模板可以保留为“示例/演示素材”，但必须明确标记为示例，不可混入真实生成结果，也不可用于伪造 AI 生成体验。

### 4.2 内容质量门（建议首期规则）

| 质量维度 | 检查要求 | 失败处理 |
|---|---|---|
| 账号定位一致性 | 内容与用户描述的领域、受众、语气不冲突 | 重新生成或提示补充定位 |
| 平台适配 | 标题、正文结构、标签符合所选平台风格 | 重新生成 |
| 信息增量 | 有具体信息、经验、步骤、观点或可验证事实，避免空话套话 | 拒绝交付 |
| 低质模板检测 | 识别套话开头、泛化结尾、重复结构和无信息量表达 | 重新生成/拒绝 |
| 合规风险 | 命中敏感主题、虚假承诺、违规引导等规则 | 人工审核或阻断 |

首期不将“质量评分达到某个固定分数”当成真理。质量检查应给出具体命中项和解释；评分阈值必须通过人工抽样校准。

## 5. 发布后数据回流：人工通道优先可用，自动通道继续增强

### 5.1 发布回填路径

现有 `publish_confirm` 已支持 `note_url`。建议把操作改成一个连续动作：

1. 用户在平台手动发布。
2. 回到 IterWave 对应草稿，点击“我已发布”。
3. 同一弹窗粘贴笔记链接（允许稍后补填）。
4. 保存后记录发布确认时间、链接和来源。
5. 用户可选择立即补充数据，或在 24 小时/7 天后收到轻量提醒。

链接校验：
- 仅允许 http/https；
- 校验域名是否与所选平台匹配；
- 不强制访问链接或要求登录第三方账号；
- 用户可以修改链接；
- 不把带有个人隐私参数的完整链接写入日志。

### 5.2 手工指标回填

提供轻量表单，首期字段：
- 曝光/播放/阅读（平台可用字段不同）；
- 点赞；
- 收藏；
- 评论；
- 分享；
- 数据统计时间。

规则：
- 每个平台只展示适用指标；
- 用户未填写的字段保持 NULL，不补 0；
- 明确数据来源为“人工填写”；
- 保存每次回填快照，不覆盖历史快照；
- 数据时间和录入时间分开记录；
- 允许修正录入错误，保留审计记录。

### 5.3 自动读回通道

继续保留平台登录态自动采集。自动采集成功时，写入来源“平台读回”；失败时不阻塞手工回填，也不把手工数据覆盖成 NULL。

同一篇内容可能同时有手工和自动数据：
- 同一指标、同一统计时间的记录按来源和时间展示；
- 复盘采用规则明确的数据版本，优先级建议为“较新且完整的可信自动读回 > 人工回填”，但不得无提示覆盖；
- 若来源冲突，标记冲突并允许用户确认。
- 任何复盘结论必须显示采用的数据来源。

### 5.4 数据结构调整建议

已有表继续复用：
- `drafts.platform_note_url`：发布链接，不重复建字段。
- `drafts.user_confirmed_at`：人工发布确认时间。
- `metrics`：逐篇指标快照。
- `contents`：内容与轮次关联。

建议新增/调整：
1. `metrics.source`：`platform_readback` / `manual` / `import`，迁移时旧记录默认 `platform_readback` 或 `unknown`，需按历史数据实际来源核定，不能盲目回填。
2. `metrics.recorded_at`（或等价字段）：记录录入时间，与指标对应的 `fetched_at`/统计时间区分。
3. 新增 `content_events`：记录 `sample_generated`、`copied`、`saved`、`rejected`、`published_confirmed`、`note_url_added`、`metrics_submitted` 等用户行为；至少包含 id、content_id、event_type、event_at、metadata_json（禁止存密钥/敏感原文）、source。
4. 新增内容来源标记：`sample` / `production`，用于隔离体验样稿与正式生产内容；可放在 contents 上，或由独立 sample_runs 关联，最终以迁移评审为准。

所有新增表/字段必须通过 SQLite migration，启动迁移需幂等；不得只在前端临时存储关键业务数据。

## 6. 轻量复盘与周报

### 6.1 复盘首页只回答三件事

1. **哪篇最好？** 展示标题、平台、关键指标、样本时间和数据来源。
2. **为什么可能表现更好？** 提取内容特征（选题、标题、结构、表达、发布时间等），并给出证据样本和样本量。
3. **下周改什么？** 给出 1-3 条可执行建议，每条说明依据、适用范围和预期验证方式。

### 6.2 证据和置信度规则

- 样本不足时明确显示“样本不足，暂不下结论”。
- 单篇内容只能描述表现，不能推断因果。
- 对比必须在同一平台、相近时间窗口和可比指标内进行。
- 建议至少展示样本数、对照范围、数据来源和更新时间。
- 旧 Analytics 高密度表格和诊断明细移入“详细数据”，不删除底层分析能力。
- 置信度必须来自可复核的样本/算法规则，不允许模型自由编造置信度数字。

### 6.3 周报

周报由以下结构组成：
- 本周表现最好的一篇（没有有效数据则明确说明）；
- 可能原因（附证据和样本量）；
- 下周建议（1-3 项，用户可采纳/忽略）。

周报只在存在足够数据时给出策略建议；数据不足时，重点引导补充发布链接或指标，不制造结论。

## 7. 指标体系与埋点

由于当前认证/租户模型不是 SaaS 用户注册体系，首期以账号组/安装实例为统计主体；未来引入真正用户体系后再增加 user_id。

| 指标 | 定义 | 口径 |
|---|---|---|
| 首次价值时间 TTV | 首次打开快速体验到首篇可用样稿展示的耗时 | 记录 p50/p90；模型等待时间单独拆分 |
| 快速体验完成率 | 提交两项信息后成功看到样稿的账号组占比 | 按新账号组 cohort |
| 7日激活率 | 初始化后 7 天内至少复制或保存 1 篇合格样稿的账号组占比 | copied 或 saved 至少一次 |
| 首次发布率 | 初始化后 7 天内至少确认发布 1 篇内容的账号组占比 | published_confirmed |
| 周采纳发布数 | 每周被采纳且确认发布的草稿数 | 北极星指标 |
| 周有效复盘数 | 每周具有可用指标且进入复盘的已发布内容数 | 过程指标 |
| 数据回流完成率 | 已确认发布且 7 天内补齐链接或至少一项指标的内容占比 | 分手工/自动来源 |

“复制或保存”应定义为用户行为，不等同于平台存草稿成功。北极星指标建议采用“每周被采纳并确认发布的内容数”；另设“每周有效复盘内容数”衡量闭环深度。

所有事件埋点需支持按账号组 cohort、平台、模型模式（托管/自带）、内容来源（体验/正式）分析。不得采集内容正文以外的无关个人信息；埋点 metadata 采用白名单。

## 8. 安全、隐私与合规约束

- 继续坚持本地优先；托管试用必须显式告知模型请求会离开本地环境。
- 供应商 API Key 仅存服务端密钥管理，不进入浏览器、数据库明文、日志、事件 metadata 或错误详情。
- 体验样稿、正式草稿、发布链接和指标数据均属于用户业务数据，按账号组隔离。
- 发布动作继续由用户完成，系统不自动点击发布。
- AI 生成标识、平台规则、敏感主题门、真人审核和频率限制分别治理；不宣传“唯一合规”或“保证不封号”。
- 对平台 URL 做域名校验和安全解析，防止任意 URL 请求、内网地址访问和 SSRF。
- 手工数据与自动数据保留来源、时间和修改轨迹。
- 提供数据导出/删除策略；删除内容时同步处理事件与指标，遵守必要审计留存规则。

## 9. API 影响（建议接口契约）

以下为拟议接口，不代表已经实现：

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/api/activation/status` | 返回快速体验可用性、模型模式、正式运营缺项 |
| POST | `/api/activation/samples` | 输入账号一句话 + 平台，创建体验生成任务 |
| GET | `/api/activation/samples/{id}` | 查询生成状态、三篇样稿和失败原因 |
| POST | `/api/contents/{id}/events` | 记录复制、保存、驳回等采用事件 |
| POST | `/api/drafts/{id}/publish_confirm` | 复用现有接口，扩展链接校验与回填体验 |
| POST | `/api/drafts/{id}/metrics/manual` | 手工提交指标快照 |
| GET | `/api/reports/weekly` | 返回周报三件事及证据 |
| GET | `/api/activation/metrics` | 返回 TTV、7日激活、首次发布等聚合指标 |

接口要求：
- 生成任务异步执行，返回 task/sample id；
- 幂等键防止重复点击生成三份样稿；
- 明确区分业务失败和系统异常；
- 错误码稳定、前端可本地化；
- 任何模型失败都不能生成模板内容；
- 新接口必须沿用当前认证和账号组隔离机制。

## 10. 状态流转

### 10.1 体验样稿

```
created
  → generating
  → quality_check
  → ready
  → adopted (copied/saved)
  → converted_to_production (optional)
```

异常分支：
- generating → failed（模型不可用/超时/额度不足/输出异常）
- quality_check → rejected（质量门不通过）
- ready → rejected_by_user（用户明确不采用）

体验样稿状态与正式轮次的 9 态状态机、草稿 8 态状态机分离，避免把无轮次样稿塞入正式生产状态机造成状态污染。

### 10.2 正式发布与数据

```
draft_pending / draft_saved
  → user_published（用户确认发布，可附 note_url）
  → metrics_pending
  → metrics_partial / metrics_ready / metrics_failed
  → analyzed
  → strategy_proposed
  → next_round
```

说明：
- `metrics_pending` 是产品展示概念，底层继续复用当前 drafts/metrics 状态字段，是否新增数据库状态需以状态机审查为准。
- 手工回填可以在自动采集失败时独立推进数据可用状态。
- 复盘状态不得仅因“自动采集失败”永久阻断。

## 11. 实施分期

### P0：质量与失败语义（先做）
- 禁止无模型时模板降级为正式内容。
- 禁止模型异常、鉴权失败、额度不足、输出无效时静默模板降级。
- 增加稳定错误码、失败原因和前端提示。
- 增加模板低质回归测试，确保不会进入正式草稿。
- 对模型调用链路补齐失败/重试/审计测试。

### P1：快速体验最小版
- 增加两项输入的快速体验入口。
- 先实现自带模型模式；托管试用作为独立部署能力，确认运营方、预算和隐私政策后再启用。
- 新增体验样稿数据标记和事件埋点。
- 展示三篇样稿、复制/保存/反馈。
- 七步 Onboarding 改为正式运营配置，不再阻断快速体验。
- 快速体验不调用平台适配器，不要求登录。

### P1：发布数据回填
- 将现有发布确认与 note_url 输入合并为一步。
- 增加链接平台域名校验和稍后补填入口。
- 增加手工指标表单、数据来源标识和历史快照。
- 自动读回失败不再阻断手工数据进入复盘。

### P1：轻量复盘
- 增加周报三件事。
- 详细指标与算法诊断折叠到二级页面。
- 为每个结论展示证据、样本量、来源、时间和限制。
- 样本不足时明确拒绝下结论。

### P2：商业化验证
- 先验证托管模型试用成本、激活转化和周采纳发布数。
- 再决定托管版、定价、套餐额度和团队能力。
- 不在没有真实使用数据前投入复杂定价页。

## 12. 验收标准

### 快速体验
- 新账号组无需平台扫码、选题库、阶段目标即可进入快速体验。
- 仅填写账号定位一句话和一个主战场平台。
- 模型可用时成功生成 3 篇样稿；TTV 统计 p50/p90。
- 无模型/无效 Key/超额/超时/输出无效时均显示明确原因，不出现模板伪稿。
- 体验样稿不进入正式轮次，不触发平台存草稿或自动发布。
- 复制、保存、驳回事件可持久化并能统计 7 日激活率。

### 数据回流
- 发布确认时可粘贴平台链接；也可稍后补填。
- 链接平台与草稿平台不匹配时拒绝或二次确认。
- 手工指标可保存历史快照；未填写字段保持 NULL。
- 自动读回和人工回填来源可区分，不互相静默覆盖。
- 自动读回失败不妨碍用户提交手工数据。

### 复盘
- 周报最多突出三项结论：最好内容、可能原因、下周建议。
- 每项结论可查看证据、样本量、来源、时间。
- 样本不足时不输出因果结论。
- 用户采纳建议后能追溯到下一轮计划/内容。

### 回归与安全
- 既有正式轮次状态机、草稿状态机和断点恢复测试全部通过。
- 既有平台登录、存草稿、人工发布红线不回退。
- 账号组隔离、密钥脱敏、备份恢复和迁移幂等测试通过。
- 不因本次改造改变现有用户数据和已发布内容。

## 13. 需要产品决策确认的事项

1. **托管模型试用是否提供？** 若提供，由谁承担 API 成本、额度上限、密钥管理、隐私告知和滥用处置？若不提供，自托管用户仍需先配置自己的模型，不能承诺无 Key 体验。
2. **ICP A/B 的原始定义是什么？** 当前审核意见未提供，临时 ICP 不能替代最终选择。
3. **体验样稿是否允许一键转为正式内容？** 建议允许，但转入后必须补齐正式内容的质量检查和来源标记。
4. **手工指标回填提醒方式？** 首期建议产品内提醒，不先接短信/邮件/微信通知。
5. **北极星口径是否接受“每周确认发布的被采纳草稿数”？** 建议将“复制/保存”用于激活，将“确认发布”用于北极星，避免同一指标混淆。

## 14. 本轮明确不做

- 不自动点击平台发布。
- 不把模板内容包装成 AI 生成。
- 不强制所有新用户先扫码登录。
- 不在缺少模型托管服务的情况下承诺无 API Key 生成。
- 不重写现有完整生产状态机。
- 不删除现有高级分析能力，只调整默认信息层级。
- 不先做复杂定价、套餐、团队协作和多租户 SaaS 化。
- 不以“唯一合规”“保证不封号”等不可证明主张作为首页卖点。

## A2. 工作包 0：现状冻结与回归基线

### 任务
- 记录 main 当前 SHA、版本基线和数据库迁移最大版本。
- 导出现有 API 路由清单：生成、轮次、草稿、发布确认、指标、复盘、模型配置。
- 梳理内容生成完整调用链：API → orchestration/round executor → content pipeline → LLM provider → quality checks → contents/drafts。
- 梳理正式轮次、草稿、读回任务三套状态机；列出所有状态写入点。
- 为模型不可用、Key 错误、超时、限流、输出解析失败建立当前行为测试。
- 对现有数据做只读迁移演练，确认 SQLite schema、索引、外键、启动迁移机制和备份恢复流程。

### 完成标准
- 有一份可追溯的 API/状态机/数据库现状清单。
- 基线环境启动、迁移、核心生成、存草稿、人工发布确认、复盘的回归测试通过。
- 基线提交可随时用于代码比较和回滚。

## A3. 工作包 1：模型失败语义与模板降级移除

### 后端改造
- 找到所有模板降级入口，不只处理 generate_copy_content 主函数；全仓搜索 template fallback、fallback content、default copy 等实现。
- 正式生产和体验生成共享统一的模型可用性校验，但错误上下文按调用场景返回。
- 将“模型未配置”“鉴权失败”“额度不足”“限流”“超时”“供应商不可用”“输出解析失败”“质量门拒绝”区分为稳定错误码。
- 模型调用异常不得被宽泛 except 吞掉后继续模板生成。
- 允许有限次数重试：仅对可重试错误（超时、临时 5xx、限流且有 Retry-After）执行指数退避；鉴权失败、额度耗尽不重试。
- 失败的生成不得计入成功生成额度；若有请求成本统计，区分请求次数、成功次数、供应商实际计费次数。
- 保留模板作为显式 demo fixture，不得写入正式 contents/drafts，不得进入复盘样本。

### 前端改造
- 模型未配置：主操作按钮置为不可执行，并提供“去配置模型”入口。
- Key 无效：显示“模型鉴权失败，请检查密钥”，不暴露 Key、供应商响应正文或环境变量名。
- 额度/限流/超时：显示可行动说明和重试条件。
- 质量门拒绝：展示具体原因，提供修改定位/重新生成；不得把失败项显示为可发布草稿。

### 测试
- 无模型配置：0 条正式内容、0 条草稿、明确错误码。
- 无效 Key：不产生模板内容，不扣成功生成额度。
- 超时/供应商 5xx：按策略有限重试，最终失败状态准确。
- 输出空白/非 JSON/字段缺失：解析失败，不生成占位文案。
- 模板 demo fixture 不可通过生产 API 路径触发。
- 失败轮次的运行报告保留错误类型和阶段，但不得记录敏感信息。

## A4. 工作包 2：体验样稿后端领域模型

### 数据实体建议

优先新增独立的 sample_runs / sample_contents（或等价结构），不建议把无轮次体验样稿强行塞入现有正式 rounds 状态机。

**sample_runs**
- id：主键，随机不可猜测 ID。
- account_group_id：账号组隔离键。
- platform：用户选择的主战场平台。
- account_description：一句话定位；按数据保留策略管理。
- status：created / generating / quality_check / ready / failed / rejected。
- model_mode：byok / hosted_trial。
- error_code、error_message_safe：稳定错误码和脱敏提示。
- created_at、started_at、completed_at。
- idempotency_key：避免用户重复点击导致重复任务。
- usage_snapshot：记录试用额度扣减依据，不存密钥。

**sample_contents**
- id、sample_run_id、account_group_id。
- title、body、hashtags（沿用项目当前内容结构，不重复发明不兼容格式）。
- angle/topic：生成角度和选题依据。
- quality_status、quality_findings_json。
- adopted_at、rejected_at。
- created_at、updated_at。

**content_events**
- id、account_group_id、content_id 或 sample_content_id（二者至少一个）。
- event_type：copied / saved / rejected / converted / published_confirmed / metrics_submitted。
- event_at、source、metadata_json。
- metadata 白名单字段，不存 API Key、Cookie、完整正文或无关个人信息。

注意：如项目已有通用事件表、草稿采用字段或审计表，应优先扩展复用，避免重复造表。所有表必须有 account_group_id，并建立按账号组和时间查询的索引。

### 状态约束
- sample_runs.status 只表达体验生成任务状态。
- sample_contents 的采用状态独立记录，避免一条 run 的三篇样稿无法分别采用。
- 一篇样稿复制不等于整批 run 完成采用。
- 失败任务可以重试，但重试必须新建 attempt 或记录 attempt_count，不覆盖首次失败证据。

### API 契约细化
`POST /api/activation/samples`
请求：
- account_description：必填，建议 10-300 字符，限制长度和控制字符。
- platform：必填，枚举值必须来自后端平台注册表。
- idempotency_key：必填或由前端生成并透传。
响应：
- sample_run_id、status、created_at、poll_after_ms。

`GET /api/activation/samples/{id}`
响应：
- run 状态；
- 三篇样稿的结构化字段；
- 每篇质量检查结果；
- 安全错误码与用户可读提示；
- 不返回供应商原始响应、密钥、内部堆栈。

`POST /api/activation/samples/{id}/contents/{content_id}/events`
请求 event_type 仅允许 copied / saved / rejected / converted。
后端验证 content_id 属于该 run 和当前账号组；事件幂等，重复复制事件可按产品统计策略去重或计数，但必须定义口径。

### 并发与成本控制
- 每个账号组同时最多一个体验生成任务（初始建议值，需配置化）。
- 每次体验固定最多 3 篇；单篇 token 上限和总 token 预算配置化。
- 超时、并发、每日体验次数均配置化，不硬编码在页面。
- hosted_trial 模式下先预占额度，成功后结算；失败按实际供应商计费规则处理，用户“成功生成额度”不因失败扣减。
- 任务取消后停止后续生成，已产生的供应商费用按实际成本记账。

## A5. 工作包 3：快速体验前端详细交互

### 页面状态
1. idle：输入账号定位和平台。
2. validating：校验输入和模型服务状态。
3. submitting：提交任务，防重复点击。
4. generating：展示任务进度，不伪造百分比；只显示真实阶段。
5. ready：展示三篇样稿。
6. partial_ready：若产品允许部分成功，清楚标注成功篇数和失败篇数；首期更建议整批成功/失败，降低语义复杂度。
7. failed：显示错误原因和可执行动作。
8. adopted：展示复制/保存状态，但仍允许用户继续查看其他样稿。

### 样稿卡片动作
- 复制正文：复制成功后记录 copied；复制失败不记成功事件。
- 保存：保存到本地体验草稿区，成功后记录 saved。
- 不合适：选择原因（定位不符、内容空泛、平台不适配、事实不准确、表达风格不符、其他），允许补充短文本。
- 转为正式内容：进入正式内容资产前重新执行正式质量检查；不自动加入发布队列。
- 体验样稿必须有明显“体验样稿”标识，不能与正式草稿混淆。

### 空状态与引导
- 没有模型：解释需要模型服务，按钮跳到最短配置入口。
- 模型服务不可用：显示服务状态和重试入口。
- 已有样稿：返回后恢复未完成的样稿结果，避免重复消耗模型调用。
- 用户拒绝配置平台登录：不影响体验生成、复制和手工发布链接回填。

## A6. 工作包 4：发布确认与手工指标回填

### 发布确认流程
- 对已有 `POST /api/drafts/{draft_id}/publish_confirm` 做兼容扩展，不另建第二套发布确认状态。
- 前端发布确认弹窗允许 note_url 为空；用户可稍后补填。
- 如果填写链接，后端校验 scheme、host、长度；平台域名白名单由平台配置提供。
- 禁止后端直接请求用户粘贴的链接；若未来需要解析页面元数据，必须单独做 SSRF 安全设计。
- 已确认发布的草稿允许修正链接，记录变更事件。

### 手工指标模型
先核对现有 metrics 表结构。若 metrics 当前是一条内容一行的宽表，优先在不破坏历史数据的前提下扩展 source / measured_at / recorded_at；若需要保留多次快照，则新增 metric_snapshots，避免覆盖历史值。

字段概念：
- content_id / draft_id；
- platform；
- impressions_or_views；
- likes、comments、favorites、shares；
- measured_at：指标对应的平台统计时间；
- recorded_at：用户提交时间；
- source：manual / platform_readback / import；
- source_ref：可选采集任务或导入批次引用；
- created_by / account_group_id；
- correction_of：修正历史记录时指向原记录。

字段口径由平台适配器定义，不将不同平台语义不同的指标强行当成同一指标。

### 数据冲突规则
- 同一平台、同一内容、同一指标、同一 measured_at 可存在多个来源记录。
- 默认不覆盖旧记录。
- 复盘选择数据时记录所选快照 ID 和选择原因。
- 数据冲突时显示“数据来源不同”，用户可查看，不自动把低优先级数据删除。
- 所有未填写的数值保持 NULL。

## A7. 工作包 5：周报与分析证据

### 计算层与文案层分离
- 计算层产出结构化事实：候选最佳内容、比较样本、指标差异、内容特征、样本量、数据来源、时间窗口。
- 模型只负责将结构化证据解释成易读建议，不允许模型编造指标、样本量、显著性或置信度。
- 每条建议必须带 evidence_content_ids、metric_snapshot_ids、sample_size、platform、time_window。
- 缺少证据时返回 insufficient_data，不生成策略建议。

### 最佳内容排序
- 不跨平台直接比较绝对播放量。
- 首期优先在同平台内按用户指定的主指标排序。
- 只有指标定义、统计窗口和样本条件一致时才比较。
- 用户未指定主指标时，展示多指标概览，不擅自把点赞数当成唯一表现指标。

### 周报 API
`GET /api/reports/weekly?week_start=YYYY-MM-DD&platform=...`
响应建议：
- period；
- best_content（可为空）；
- why_it_may_work（结构化证据列表）；
- next_actions（最多 3 项）；
- sample_size；
- data_sources；
- limitations；
- generated_at。

## A8. 工作包 6：事件、指标和分析口径

### 事件字典
| 事件 | 触发条件 | 去重/统计 |
|---|---|---|
| activation_started | 首次进入快速体验 | 账号组首次一次 |
| sample_generation_started | 后端任务创建成功 | 每个 run 一次 |
| sample_generation_succeeded | 样稿达到 ready | 每个 run 一次 |
| sample_generation_failed | run 最终失败 | 每个 run 一次，记录错误码 |
| content_copied | 浏览器复制 API 成功 | 每次成功复制，激活按账号组去重 |
| content_saved | 保存接口事务成功 | 每篇内容首次采用去重 |
| content_rejected | 用户提交不采用 | 每篇内容可多次反馈但保留最新状态和事件历史 |
| publish_confirmed | 发布确认事务成功 | 每篇正式内容首次确认 |
| note_url_added | 链接首次保存/补充 | 每次变更留事件 |
| metrics_submitted | 指标快照写入成功 | 每个快照一次 |
| weekly_report_viewed | 周报实际加载成功 | 按账号组/周统计 |

### 指标公式
- TTV = first_sample_ready_at - activation_started_at；同时记录模型等待、生成处理、前端展示耗时。
- 7 日激活率 = 初始化 cohort 中 7 天内至少有一篇样稿 copied 或 saved 的账号组数 / cohort 账号组数。
- 首次发布率 = cohort 中 7 天内至少有一篇内容 publish_confirmed 的账号组数 / cohort 账号组数。
- 周采纳发布数 = 周内状态为 publish_confirmed 且有采用事件的去重内容数。
- 数据回流完成率 = 确认发布后 7 天内至少有一个有效指标快照的内容数 / 确认发布内容数。
- 有效复盘数 = 满足最小数据完整度、进入分析计算的发布内容数。

### 防止指标失真
- 新账号组 cohort 的创建时间定义必须固定；历史账号组不纳入新用户激活率分母。
- 未完成 7 天观察窗的 cohort 不进入完整 7 日激活率分母。
- 复制事件只能在客户端确认 clipboard write 成功后上报；浏览器不支持时提示用户手动复制，不记成功。
- “保存”必须以后端事务成功为准。
- 数据指标按账号组隔离；禁止从前端传 account_group_id 决定归属，必须由服务端认证上下文解析。

## A9. 数据迁移、回滚与兼容

### 迁移原则
- 新表/字段先加后用，旧代码在迁移后仍可运行。
- 对历史记录新增 source 字段时，只有在历史来源可确定时才回填；无法确认填 unknown，不猜测。
- 新增索引前评估 SQLite 写锁和表大小。
- migration 必须幂等，重复启动不重复创建/破坏数据。
- 迁移前自动备份；备份失败时停止迁移。
- 不对现有 contents/drafts/metrics 做 destructive rewrite。

### 回滚策略
- 前端功能可通过 feature flag 关闭。
- 新接口关闭后，旧生产、草稿、发布确认流程仍可运行。
- 新增表保留，不在回滚时自动删除用户体验数据。
- 数据库降级不执行破坏性反向迁移；回滚代码后保留兼容字段。
- 每个工作包独立 PR，避免一次大改造成无法定位的回归。

## A10. 工作包 7：托管模型试用的单独技术方案

仅在产品决策明确提供托管试用后实施。

### 架构
浏览器 → IterWave API → 托管模型网关 → 模型供应商。

浏览器不直接访问供应商，不接触服务端 Key。托管网关应支持：
- provider/model allowlist；
- account_group_id 维度额度；
- 请求/Token/成本限额；
- 并发和速率限制；
- 供应商熔断和超时；
- 幂等、审计、成本报表；
- 用户输入数据告知、保留期限和删除流程；
- 试用额度耗尽后引导 BYOK。

### 试用额度扣减
- 任务创建时预占；
- 任务完成后按供应商真实 usage 结算；
- 失败且供应商未计费则释放预占；
- 供应商已计费但生成失败时，用户可用额度是否退还由产品政策定义，但必须区分用户额度与运营成本。
- 不把“失败不扣用户额度”误解成“失败没有供应商成本”。
