# 全局任务队列与账号组运行时隔离设计

## 目标与边界

IterWave 是单一运营者使用的运营工作台。客户是业务归属，账号组是实际执行单元。全局任务队列服务于运营者本人，不引入客户登录、客户自助注册、客户账单或客户 API Key。

核心不变量：

1. 当前页面选中的账号组只决定前台请求上下文，不决定后台任务上下文。
2. 每个后台任务提交时必须固化 `tenant_id`、业务对象 ID 和执行参数。
3. 内容生产、平台存草稿及账号组级 APScheduler 定时作业由同一个全局消费者串行执行；热点采集仍由独立全局服务管理。
4. 队列存储在共享 `shared/system.db`，不属于任何一个账号组的 `easel.db`。
5. 消费者执行任务时显式构造任务所属账号组的运行时；禁止依赖 `_g_ctx`、活动账号组或模块级可变登录目录。
6. 任务失败不能阻塞后续任务；任务执行结果与日志写入任务所属账号组数据库。
7. 用户主动切换账号组不取消、暂停、重排或等待队列中的任务。

## 队列模型

首期采用全局 FIFO、单消费者：

- FIFO 排序键：事务内递增分配的 `queue_order ASC`，不依赖时间戳精度或随机任务 ID。延迟任务另存 `available_at`；未到执行时间的任务不阻塞已到期任务，到期任务仍按队列序号排序。
- 当前任务类型覆盖生产轮次、恢复存草稿，以及发布轮询、数据采集、每日主动运营（评论/关注）、被动评论轮询、熔断恢复、选题库扫描/同步、数据保留清理、轮次超时扫描、轮次复盘和自动闭环触发。以上账号组级作业统一排入全局 FIFO；热点采集使用独立全局服务，不依赖账号组登录态。
- 热点采集/标签匹配/研判不使用平台登录态，保留独立 single-flight 资源池；每次执行固化发起时的 tenant_id、配置对象和独立 SQLite 连接。账号组切换不等待、不取消、不重置该服务；热点状态只向所属账号组返回。另一个账号组在服务忙碌时收到 409，明确提示稍后重试，不静默丢弃请求。
- 队列状态：`queued → running → succeeded | failed`；用户可取消 queued；进程中断且租约过期转为 `interrupted`。
- 同一 `tenant_id + task_type + aggregate_id` 不允许同时存在多个 queued/running 任务，避免同一轮次重复提交。
- 单消费者通过 system.db 中的全局 worker lease 协调，避免多 Uvicorn worker 同时执行不同任务。
- 队列任务默认不自动重试有外部副作用的动作。进程中断时标记 interrupted，经过业务恢复检查后由操作者重新入队，避免重复存草稿或重复平台操作。
- 服务重启后 queued 任务保留并继续排队；租约过期的 running 任务转 interrupted，不盲目重放。

## 任务上下文

任务载荷至少包含：

- `task_id`
- `task_type`
- `tenant_id`
- `round_id` 或其它业务对象 ID
- 提交时明确的运行参数
- 配置/计划版本标识（后续补齐）

消费者按 tenant_id 通过 TenantRegistry.paths() 获取路径，独立加载该账号组配置、数据库连接、业务数据、素材目录、浏览器 profile 和平台 storage_state。所有连接、浏览器上下文和执行器在任务完成后关闭。

**禁止**在执行过程中通过 `TenantRegistry.active_id()` 或 `_g_ctx` 推断任务归属。

## 登录态隔离

当前 `account_login` 和 `login_manager` 通过模块级变量保存登录目录。此设计不适用于后台任务跨账号组执行。

改造方向：

- `login_manager` 的 storage_state 路径必须来自任务上下文/显式参数；过渡期可用 ContextVar，但必须由任务执行器在 try/finally 中设置和恢复。
- `account_login` 的扫码登录进程、二维码、临时状态和导出任务必须按 tenant_id + platform 管理，不能仅用 platform 作为进程字典键。
- `_build_tenant_runtime_context()` 只能构造上下文，不得改变任何模块级目录或全局活动账号组。
- 切换账号组不再终止其他账号组已提交的 Agent 任务；交互式扫码登录也必须按账号组隔离。

## 即时热切换开关与验收前置条件

即时热切换由部署环境变量控制，不属于 `config/config.yaml` 中的业务配置：

```bash
ITERWAVE_ENABLE_TENANT_HOT_SWITCH=1
```

- 当前主分支默认启用：未设置该变量时即时热切换开启。只有显式设置为空字符串或 `0/false/no/off/disabled`（忽略大小写与首尾空格）才关闭；其他非空值均视为开启。
- 关闭时，`/api/tenants/select` 只保存所选账号组，并返回需要重启后生效的提示；这不是即时运行时切换。
- 开启时，账号组选择才会即时切换前台运行时引用，常驻后台调度器、连接和已入队任务不因前台切换而停止。
- 修改环境变量后必须重启服务，确保进程读取到新值。正常部署无需为了开启即时热切换额外添加该变量；只有明确需要关闭时才设置为上述 false 类值。
- **真机验收前置步骤：** 确认运行进程没有显式设置 false 类值；重启部署服务以确保运行的是目标主分支版本。调用账号组选择接口，确认返回 `restart_required=false`、`switch_status=completed`。随后执行 A/B/C FIFO、执行期间切换和登录态隔离测试。
- 如果没有启用该开关，切换账号组后重启服务会使原 `running` 任务在恢复流程中进入 `interrupted`。这不是队列被切换操作取消，而是进程重启后的安全中断状态；不得用重启替代热切换验收。
- 验收环境应使用已完成登录的账号组。切换时仍进行中的交互式扫码登录不在本轮验收范围内。

## 前台切换与调度器

- 前台切换只更新活动账号组指针和前台运行时引用。
- 应用启动时为注册表中所有账号组建立常驻运行时与 APScheduler，并各自持有独立数据库连接；新建账号组在首次即时切换时初始化。单个账号组初始化失败只记录该组错误，不阻止其他账号组继续运行，切换到该组时再重试。
- 前台切换只替换 `_g_ctx` 指向的前台上下文，不 quiesce/shutdown 旧账号组调度器，也不关闭旧账号组数据库连接。所有常驻调度器仅在应用关闭时统一停止并释放连接。
- 不等待全局任务队列 drain，也不关闭任务消费者持有的连接。现有切换流程仍会停止前台账号组的交互式扫码登录进程；扫码登录进程按 tenant_id + platform 隔离是后续整改项，不应与队列消费者混为一谈。
- 每个账号组的定时作业通过 SchedulerEngine._invoke 写入全局队列，由 worker 在任务所属账号组运行时中执行；APScheduler 只负责定时触发，不直接执行账号组业务作业。
- APScheduler 的生命周期与全局任务消费者生命周期分离。活动账号组切换不应启动/停止全局消费者。

## 系统级模型配置

- `llm.*` 配置存放在共享 `system.db`，不再由各账号组分别覆盖。
- API Key 仍只保存在部署环境的 `.env`，不写入 system.db 或账号组数据库。
- 首次迁移时，以服务启动时当前活动账号组的有效模型配置作为共享初始值；后续账号组中不一致的历史值写入迁移冲突审计，再从其租户设置中清除。
- 迁移后所有账号组加载顺序为：部署配置 → 账号组业务设置 → 系统级模型设置；系统级模型设置最后覆盖，确保所有客户使用同一模型配置。
- 模型配置修改只写 system.db；混合提交系统级模型配置与账号组业务配置会被拒绝，避免跨两个 SQLite 数据库无法原子提交的问题。
- 模型调用量与成本后续按 tenant_id 记录，用于运营者内部核算，不生成客户账单。

## 失败恢复与幂等

- enqueue 必须在 system.db 事务中持久化。
- 轮次 ID 作为 aggregate_id，数据库部分唯一索引防止重复活动任务。
- queued 任务在重启后继续执行。
- running 任务通过 lease 识别消费者失联；过期后进入 interrupted，不自动重放有副作用任务。
- 任务状态变更必须由持有 lease 的 worker 完成。
- 取消只允许 queued；running 取消必须等实现可验证的安全取消点后再开放。

## 验收测试

1. A、B、C 依次提交任务，队列严格 A → B → C。
2. A 执行期间连续切换 B、C，A 的数据库、素材和登录态不变。
3. A 完成后 B 执行，B 完成后 C 执行。
4. 一个任务失败，后续任务仍继续。
5. 同一轮次重复提交只生成一个活动队列任务。
6. 两个 API worker 同时启动时，只允许一个全局消费者执行任务。
7. 服务重启后 queued 任务继续；running 任务安全进入 interrupted。
8. 任务状态查询不能把其它账号组的业务结果混入当前账号组内容页面。
9. 执行器不得读取当前活动账号组或模块级可变登录目录。
10. 平台账号同组同平台最多一条，数据库并发写入也必须失败关闭。


## 部署进程数约束

当前应用 lifespan 会在每个 Uvicorn 进程内启动各账号组 APScheduler。全局任务消费者通过 system.db 租约实现跨进程单消费者，但 APScheduler 本身尚无跨进程 leader election；多个 Uvicorn worker 可能重复触发同一批定时作业。**当前部署必须使用单个 Uvicorn worker**（默认启动方式即可），在实现并验证调度器选主前，不得通过 `--workers N` 扩容。此限制不影响单进程内 A/B/C 前台切换和全局 FIFO 队列。

## 停机与崩溃恢复（2026-10-31）

- **进程异常退出 / SIGKILL：** 当前部署必须是单 Uvicorn worker。新进程启动时会立即把上一实例遗留的全部 `running` 任务标记为 `interrupted`，不再等待 90 秒租约过期；租约过期恢复仍保留作兜底。queued 任务保持原顺序继续执行。
- **正常 SIGTERM：** Worker 默认给正在执行的任务 30 秒宽限期。对可协作取消的异步任务，宽限期内完成则正常落 succeeded；超时则取消协程并将任务标记为 `interrupted`，错误码为 `worker_shutdown`。可通过部署环境变量 `ITERWAVE_TASK_SHUTDOWN_GRACE_SECONDS` 设置 0–300 秒，默认 30 秒。**注意：** 若任务正处于不让出事件循环的同步阻塞调用，Python 无法在该调用返回前处理停机事件；线程心跳可维持租约，但不能强行中断同步调用。应避免在事件循环中执行长时间同步 I/O，部署停止超时仍需覆盖最长不可中断调用时长。
- systemd / 容器编排的停止超时应大于上述宽限期并留出应用清理余量。停机中断的任务不得自动重放；必须先核实平台侧是否已存草稿/执行外部动作，再人工恢复。
- 心跳续租在线程中执行，不依赖 asyncio 事件循环调度；同步 I/O 阻塞事件循环时，不会因此停止续租。

## 本轮技术债清理

- 删除未参与任务状态判定的进程级 `_running_rounds` 集合，轮次运行状态统一以当前账号组队列 / 轮次数据库为准；备份恢复检查也只检查当前账号组任务，避免不同账号组相同轮次 ID 相互阻塞。
- 队列列表遇到单条损坏 payload 时记录 task_id 和错误并跳过该行，不再让整页列表请求失败。
- 当前队列不实现自动重试（外部平台动作不具备通用安全重试语义）；入队时明确拒绝 `max_attempts != 1`，避免字段看似支持多次尝试但实际上从不重试。
- 图片生成与图片质量工具的任务 API 调用显式传入当前账号组 cfg；工具函数保留 cfg 缺省值仅用于独立脚本/兼容调用。后续新增后台调用必须显式传入租户 cfg。
- 仍需后续单独审计其它模块的全局配置单例读取；本次不宣称已完成所有模块的全局配置注入重构。
