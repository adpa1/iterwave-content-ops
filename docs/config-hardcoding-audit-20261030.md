审查日期：2026-10-30  
审查基线：`fix/ux-data-leak-and-media-config-20261030`（PR #42 head，叠加 PR #41）  
范围：仓库 217 个跟踪文件，重点覆盖 Python 配置模型、配置校验/持久化/API、热点采集与匹配、评分、媒体处理、自动闭环、调度、前端配置编辑器、数据库迁移和测试。

## 一、审查结论

**配置中心基础链路已经建立，但不能认定全系统配置化完成。**

目前运行时配置的实际主链路是：`config.yaml` 提供初始配置 → Pydantic `Config` 校验 → 账号组 SQLite `tenant_settings` 保存运行时覆盖 → 启动/热切换时 `apply_overrides` 套用 → `patch_config` 更新内存对象并持久化版本、审计。旧 `config_overrides.json` 只应保留为一次性迁移和故障恢复兼容来源。

本轮发现的主要问题不是“没有配置中心”，而是：
1. 部分业务策略仍直接写在执行代码里。
2. 有些参数已经在 Pydantic 模型或白名单中，但配置元数据接口没有完整暴露。
3. 有些后端允许修改的字段没有对应的配置中心编辑入口。
4. 有些配置模型字段声明存在，但运行代码根本不读取，形成无效配置。
5. 少数模块保留旧 JSON 持久化实现和过时注释，容易让维护者误判当前事实来源。

## 三、已存在但配置链路不完整的字段

### 3.1 配置元数据接口遗漏

`config_metadata_view()` 当前主要从 `SCALAR_RULES`、`STRING_RULES`、`LIST_RULES` 自动生成元数据，再单独处理配额、调度任务和三模式评分权重。但 `_validate()` 中还有独立分支，这些字段没有完整进入元数据：

- `scoring.active_dimension_min_uses`
- `scoring.active_dimension_window_days`
- `scoring.shrinkage_m`
- `rhythm.intervals.*`
- `hot_topics.dedup.cross_platform_similarity`
- `platforms.<platform>.enabled`
- `topic_kb.type`、`topic_kb.field_mapping`
- `ultimate_goal.goal_mode`、`ultimate_goal.positioning`、平台画像与平台协同字段
- `timeouts.metrics_retry_policy`（当前为字符串，后续改为结构化字段）
- 若干专用编辑器使用的字段没有统一元数据声明。

本轮已将上述独立校验字段补入统一元数据；专用编辑器继续负责高级评分、节奏间隔、选题库、账号画像等复杂结构，普通运行策略由 RuntimePolicyEditor 统一编辑。新增测试强制要求所有 SCALAR_RULES 白名单字段都必须出现在配置元数据中。

### 3.2 配置中心前端遗漏

- `TimeoutEditor` 没有编辑 `timeouts.goal_max_rounds` 和 `timeouts.round_min_interval_hours`。
- `timeouts.metrics_retry_policy` 既缺少结构化校验，也没有可用编辑控件。
- `RuntimePolicyEditor` 不支持布尔值的正确输入/提交语义；如果后续直接把布尔策略加进分组，会以字符串提交并被后端拒绝。
- 热点采集/趋势策略、自动闭环反馈策略尚无专用编辑区。
- 元数据类型、后端白名单、前端编辑器目前分散维护，缺少覆盖性测试防止字段漏配。

## 四、无效或重复配置

- `CircuitBreakerConfig.signals` 与 `CircuitBreakerConfig.recovery` 曾在模型和 YAML 中声明，但恢复执行逻辑固定执行“冷却到期、登录验证、轻量动作验证”三步；运行代码没有读取这两个字段。本轮已删除无效配置项，三步恢复继续作为不可关闭的安全流程。
- `config_store.py` 的正常 `patch_config()` 只写 SQLite；旧 `_save_overrides()` 仅保留为显式 JSON 迁移/恢复兼容工具和测试工具，不在正常运行时配置更新链路中调用。
- `config_overrides.json` 仍用于一次性迁移/故障回退；这属于兼容路径，不是日常配置事实来源。迁移源文件保留用于回滚，不应继续被正常写入。
- YAML 初始值与 Pydantic 默认值存在重复，这是启动默认配置与缺省兜底的必要双层定义；必须通过测试保持一致，不应简单删除其中一层。
- 媒体生成像素/尺寸/响应体上限、备份容量上限存在“配置上限 + 代码硬上限”双重限制，这是有意的安全边界，必须保留“配置只能收紧，不能放宽”的行为。

## 五、应继续保留在代码中的常量

以下内容不是运营参数，不应为消灭数字而放入数据库：

- 安全上限和防护边界：`safe_http.py` 的重定向次数、网络超时/响应体上限；`kb_sources.py` 的上传大小、Excel 展开大小/行数/列数限制；图片生成最大尺寸/像素/响应体代码硬上限；备份最大容量代码硬上限；认证、会话、路径隔离和输入长度安全限制。
- 协议和数据结构：平台枚举、数据库状态值、SQL 结构、JSON 响应格式、哈希/ID 算法、HTTP 状态码、文件格式标识、迁移版本号。
- 安全流程：发布人工确认闸门、维度匹配门、可发布性门、熔断三步恢复门、账号组隔离与 fail-closed 行为。
- 数学定义：百分位插值、评分归一化公式、指数衰减公式、比例换算等算法定义；其业务参数可以配置，但公式本身应版本化。
- 纯视觉实现细节：卡片像素坐标、字体尺寸、颜色、边距、渐变、折行算法；除非产品明确需要用户自定义主题，否则不进入运行配置。
- 平台协议适配细节和提示词版本标识：随代码版本发布，避免管理员通过配置破坏协议/安全要求。

## 六、改造原则与验收标准

1. SQLite 账号组配置是运行时覆盖值的唯一持久化事实来源；YAML 只负责初始默认值，旧 JSON 只负责迁移/兼容读取。
2. 业务阈值、运营策略、算法参数、可调时限和重试策略进入类型化配置模型、后端白名单校验、SQLite 持久化、元数据接口和前端编辑器。
3. 密钥只在环境变量/密钥存储中；服务端点、平台内部 account_key 等部署或内部路由字段不下发到普通配置元数据，不允许普通用户通过未展示字段绕过配置中心。
4. 配置只能在安全硬上限内调整；跨字段关系（例如阈值大小、权重合计、超时先后关系）必须在一次批量 PATCH 的最终状态上校验。
5. 对每个可在线调整字段建立覆盖测试：默认值、合法更新、非法值、持久化、重启/热切换回读、元数据可见性、UI 输入类型。\n6. 平台 account_key、适配器端点、Webhook 环境变量名和服务密钥变量名属于内部/部署信息，不出现在普通配置 API、诊断文案和页面中；普通 PATCH 也拒绝修改这些隐藏字段。
6. 审查报告随代码提交；所有自动化测试通过后，才进入 PR 链逐级合并。真机平台登录态/账号组切换验收由用户执行，未验收前保持热切换功能开关关闭。

## 八、补充安全审查结果

专项审查还发现此前的内部信息隐藏只覆盖了部分接口，存在以下遗漏，本轮已修复：

- `current_config_view()` 曾把平台 `account_key` 和 `base_url` 返回前端；平台设置页也曾提供这两个字段的编辑框。现只返回平台启用状态，普通 PATCH 拒绝修改平台内部标识和适配器地址。
- 配置历史/覆盖视图的内部字段脱敏集合已覆盖平台端点与账号内部标识。
- Webhook 的 `webhook_url_env`、LLM API Key 写入接口的环境文件路径不再出现在响应结构中；通知页面只显示是否配置。
- 图片生成缺少密钥时不再把环境变量名拼入错误信息；流程诊断也不再显示 `llm.api_key_env`。
- 服务端点和密钥变量名仍可在服务端部署配置中使用，但不会通过普通配置中心 API 下发或修改。

## 九、当前交付范围与保留边界

本轮没有把所有数字都搬进数据库。以下值继续保留在代码中，且属于明确的设计边界：

- 安全与资源硬上限：网络响应体、重定向次数、上传/展开大小、像素/图像大小、备份容量、登录数据目录权限、租户 ID 格式、认证与会话限制。
- 不可关闭的安全门：发布人工确认、可发布性检查、账号组隔离、熔断三步恢复、失败关闭策略。
- 协议与算法定义：平台状态/事件枚举、JSON 协议、哈希与 ID 生成、评分公式、相似度计算公式、提示词版本。
- 前端纯展示实现：卡片尺寸、像素坐标、颜色、间距和截断展示样式。

运行配置只控制安全边界以内的参数；配置中心新增字段必须同时具备 Pydantic 类型定义、后端白名单与关系校验、SQLite 持久化、元数据、编辑器和测试。
